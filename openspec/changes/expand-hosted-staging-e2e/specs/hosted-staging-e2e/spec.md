## ADDED Requirements

### Requirement: Hosted staging runtime separation

The project SHALL provide an explicit hosted staging Playwright configuration
that targets the deployed frontend URL, uses the real Supabase runtime, and does
not start a local development server or enable mock adapters.

#### Scenario: Running the hosted staging suite

- **WHEN** an authorized operator runs the staging E2E command with the required
  staging environment variables
- **THEN** the browser navigates to the configured hosted base URL
- **AND** the application uses Supabase Auth and persisted adapters
- **AND** no local Vite server or mock-backend flag is used

### Requirement: Staging test data isolation and cleanup

Hosted staging E2E SHALL use the currently authorized staging identity and
active bakery boundary, avoid mutating existing records by default, tag
run-created records with a unique run identifier where supported, and remove or
expire those records through a secure cleanup path after success or failure.

#### Scenario: Two hosted runs execute against staging

- **WHEN** two staging runs create customers, recipes, orders, or invitations in
  the authorized staging bakery
- **THEN** each run uses unique, bakery-scoped records
- **AND** assertions do not depend on another run's records
- **AND** cleanup for one run does not remove the other run's records

#### Scenario: A hosted run fails midway

- **WHEN** a staging test fails after creating external records
- **THEN** cleanup executes from a `finally` path or recoverable cleanup job
- **AND** service-role credentials, if required for cleanup, remain server-side
- **AND** the test report identifies cleanup status without printing secrets

### Requirement: Hosted authentication and workspace acceptance

The staging suite SHALL verify real authentication, session reload, bakery
selection, direct protected-route access, logout, and bakery-scoped membership
behavior using the currently authorized staging identity.

#### Scenario: Authenticated user reloads a protected route

- **WHEN** the staging user signs in, enters the authorized active bakery, opens a
  canonical workspace route, and reloads the page
- **THEN** the session remains valid or the UI presents the supported re-auth
  path
- **AND** the requested route remains under the hosted base path
- **AND** the workspace displays records from the active bakery only

#### Scenario: User cannot cross bakery boundaries

- **WHEN** the staging suite switches between authorized test bakeries or
  attempts to address an out-of-scope bakery record
- **THEN** only memberships authorized for the signed-in user are available
- **AND** out-of-scope records are not displayed or mutated
- **AND** the result is recorded as tenant-isolation evidence

### Requirement: Persisted critical feature journeys

The hosted suite SHALL verify create or update, immediate rendering, reload
hydration, and cleanup for each declared persisted capability that is deployed
to staging, including orders, customers, recipes, inventory, production flows,
invoices/payments, and workspace invitations.

#### Scenario: Persisted feature is declared staging-ready

- **WHEN** its owning migration, adapter, and UI deployment are included in the
  staging release
- **THEN** the corresponding E2E journey creates or updates a run-scoped record
- **AND** the record appears immediately in the owning screen
- **AND** a reload retrieves the authoritative persisted state
- **AND** the record is removed or safely expired during cleanup

#### Scenario: Persisted feature is not staging-ready

- **WHEN** the preflight detects that the owning migration, function, or adapter
  is not deployed
- **THEN** the feature journey fails with a named readiness prerequisite
- **AND** it does not fall back to mock data or claim hosted acceptance

### Requirement: Hosted public and base-path routes

The deployed application SHALL support anonymous direct navigation and generated
links for the hosted base path, including workspace SPA fallbacks, public
storefronts, public invoices, and password-recovery callbacks.

#### Scenario: Anonymous user opens a generated public link

- **WHEN** the suite follows a storefront or invoice link generated by the
  hosted dashboard
- **THEN** the URL remains under `/Bakery-app/`
- **AND** the public view loads without an authenticated workspace shell
- **AND** the view displays the run's or seeded public record

#### Scenario: Anonymous user opens a recovery callback

- **WHEN** the suite opens the hosted password-recovery callback path
- **THEN** the application resolves the callback beneath `/Bakery-app/`
- **AND** it displays the supported recovery state rather than the workspace
  not-found page

### Requirement: Invitation delivery and acceptance evidence

Hosted invitation E2E SHALL verify the real Edge Function and Auth handoff when
the staging mailbox prerequisite is configured, including delivery, callback
path, invited-email matching, acceptance, membership reload, duplicate handling,
and revocation or cleanup.

#### Scenario: Invitee accepts a delivered staging invitation

- **WHEN** an authorized inviter sends a run-scoped invitation to the approved
  invitee mailbox
- **THEN** the mailbox receives a callback under `/Bakery-app/`
- **AND** the invitee signs in with the invited email
- **AND** accepting the invitation creates exactly one authorized membership
- **AND** a reload shows the new bakery without duplicate membership rows

#### Scenario: Duplicate or failed invitation is handled safely

- **WHEN** the inviter repeats a pending invitation or delivery fails
- **THEN** the UI reports the authoritative failure outcome
- **AND** duplicate pending requests are not created
- **AND** a failed delivery leaves no usable pending invitation

### Requirement: Hosted E2E evidence and release gating

The staging workflow SHALL publish reproducible test results, traces or
screenshots for failures, a readiness summary, and the exact deployed frontend
and Supabase revision context without exposing credentials or personal test data
beyond the approved staging scope.

#### Scenario: Hosted staging acceptance passes

- **WHEN** all declared preflight and desktop/mobile staging journeys pass
- **THEN** the workflow records a passing hosted E2E gate tied to the deployment
- **AND** the evidence identifies which capabilities were actually exercised

#### Scenario: Hosted staging acceptance fails

- **WHEN** any journey or prerequisite fails
- **THEN** the workflow fails the staging gate
- **AND** uploads diagnostics sufficient to reproduce the failure
- **AND** does not update release evidence to claim hosted readiness
